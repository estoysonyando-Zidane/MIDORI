# World を見る

## なぜこれが要るのか

このプロジェクトで見つかった不具合の大半は、**データが正しいまま見た目が壊れていた**ものだった。

| 不具合 | データ検査 | 型検査 | 見れば一発 |
|---|---|---|---|
| ホーム縁端の線が白（実際は青緑） | 通る | 通る | ○ |
| 信号機の頭部が列車の当たる高さ | 通る | 通る | ○ |
| 川が地面の0.18m下に埋まっている | 通る | 通る | ○ |
| 地平線が空の帯（遠クリップ面4,000m） | 通る | 通る | ○ |
| 枕木が線路と平行（軸の取り違え） | 通る | 通る | ○ |

**データ検査と型検査は、この種を1件も捕まえない。** 見るしかない。

## 手順

```
npx vite preview --host 127.0.0.1 --port 4174 --strictPort &
node scripts/capture-viewpoints.mjs            # 撮る・測る・基線と比べる
node scripts/capture-viewpoints.mjs --baseline # 意図した変更のあと基線を更新
```

出力は `build/viewpoints/` に PNG群・`contact-sheet.jpg`（一覧）・`metrics.json`。
**まずコンタクトシートを1枚見る。** 8枚を個別に眺めるより、並べたほうが破綻に気づく。

## 定点は座標で書かない

`scripts/viewpoints.json` のカメラは**名前の付いた地物からの相対位置**で書く。

```json
{ "from": { "feature": "STR_MIDORI_PLATFORM_1", "offset": [0, 1.6, 0] },
  "look": { "bearing": 146.6, "pitch": -2 } }
```

構内の寸法が変われば定点も一緒に動く。座標直書きだと、ホームを1m動かした瞬間に
全定点が無意味になる。`why` に**その定点が何を見張っているか**を必ず書く。

## 測っている量と、それが捕まえるもの

| 量 | 落ちると／跳ねると |
|---|---|
| `sky` 空の画素比 | 0.92超=カメラが上向きかWorldが無い / 0=地面に埋まっている |
| `green` 植生比 | 森を消した・間引きすぎた |
| `luma` 平均輝度 | 12未満=真っ黒 / 245超=露出破綻 |
| `contrast` 輝度の標準偏差 | 霧やライティングで潰れた |
| `edges` エッジ密度 | 0.6未満=何も建っていない。**Worldの「詰まり」の代用** |
| `unique` 量子化色数 | 40未満=単色に潰れた（描画されていない） |
| `horizon` 空が終わる行 | 地平線の高さ。カメラのピッチ異常 |
| `skyBalance` 上1/3の空 − 下1/3の空 | **負=空が下にある＝地面の下にいる**。地形は片面描画なので地下からは地面を透かして空が見え、輝度も色数もエッジも正常に見える。**これでしか捕まらない** |

**フレーム時間は測らない。** ここのラスタライザはソフトウェアで毎秒1フレーム以下。
携帯やPCのGPUの代わりにならない。描画コストは `scripts/measure-budget.mjs` が
draw call・三角形・常駐リソース・転送量として別に測る。

## WorldInspect の落とし穴

`window.__world` が World を見る唯一の窓口。

- `pause()` の後に `frames()` を呼ぶと**永久に待つ**（ループが止まっているため）。
  `look()` は同期的に描画するので、pause 後は frames を待つ必要がない。
  この罠は実際に踏んだ。今は `frames()` が明示的に投げるようにしてある。
- `centreOf()` が返すのは**バウンディングボックスの中心**。長く傾いた地物
  （川・道路・ホーム）では、中心と地面の比較は意味を持たない。13m下る川は
  中心が13m地下にあると報告されるが、配置は完全に正しい。
- `groundY()` は地形メッシュへのレイキャスト＝**表面**。生成器が使う高さ
  **関数**とは別物。この2つが食い違うのがこのプロジェクトの再発不具合で、
  駅舎が宙に浮いた原因もこれ。
- `scene()` はシーングラフそのもの。**誰も予期していなかった問いを、新しい
  メソッドを出荷するより先に聞く**ためにある。三角形の行き先の集計はこれで書けた。

## 印象を測定で検算する — 照明を打ち消す比較

「なんとなく暗い/明るい」で色を触らない。描画の画素と写真の画素は照明が
違うので直接比べられない。**同じ画面の中にある、写真から起こした基準色との
比**を取ると照明が打ち消える。

実例。コンタクトシートを見て「ホーム面が写真より暗い」と思った。検算:

```
                  ホーム面 / 縁端の青緑線（輝度比）
写真(2018)         102.3 / 207.8 = 0.492
描画               99.9 / 191.2 = 0.522     → 差6%、一致の範囲
```

縁端の青緑は写真から実測した色なので、画面内の基準として使える。
**結論: 暗すぎない。印象が誤りだった。** 不要な変更を1件防いだ。

色の領域は座標で切らず、**条件で自動的に拾う**（青緑なら G−R>40 かつ
|G−B|<35、無彩色の面なら max−min<14）。座標指定は構図が変わると外れる。

## 見つけたものの扱い

食い違いを見つけたら、**まず自分の道具を疑う**。このプロジェクトでは
QA道具自身の不具合が5件中3件だった。検査が「線路から86m離れた道路が
車両限界を侵している」と言ったときは、検査が間違っていた。

不具合を直したら、**不具合を戻して検査が落ちることを確かめる。**
一度も落ちたことのない検査は、動くと分かっていない。

この検査自体もそうやって確かめた。カメラを真上に向けた定点と地下40mに沈めた
定点を一時的に足して走らせたところ、**真上は捕まったが地下は素通りした** —
空0.76・輝度182・エッジ7.1・色数1582 と、どの閾値にも掛からなかった。
そこで `skyBalance` を足して両方が落ちることを確認した。対照の正常な定点は
同じ実行で数値が一致したまま通った。**穴は、落としてみるまで見えない。**

## やってはいけないこと

- 見栄えのために事実を曲げる。山が隠れるなら隠れたままにする。
- 基線を「赤いから」更新する。基線の更新は**意図した変更のときだけ**。
- 定点を減らして PASS にする。
